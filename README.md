# fmxai.org

The site of the Formal Methods × AI event series, generated by
[`sites`](https://github.com/for-all-dev/sites), a static site generator written and verified
in Lean 4. There is no JavaScript anywhere: the community map that used to be laid out by Z3
in Node and drawn by D3 in the browser is now computed, proven correct and printed as static
SVG by Lean.

```sh
lake build                     # library, executable, tests
.lake/build/bin/fmxai build    # writes dist/
.lake/build/bin/fmxai serve    # http://127.0.0.1:8080/, pages from memory, assets from public/
scripts/check.sh               # everything above plus escape-hatch audit and leanchecker
```

With Nix, `nix develop` provides `elan`, which picks up `lean-toolchain`.

## Layout of the repository

| Path | What it is |
| --- | --- |
| `Fmxai/Route.lean` | The four routes, and the header, footer and other shared markup. |
| `Fmxai/Pages/*.lean` | The pages, as Lean terms in the typed HTML DSL. |
| `Fmxai/Site.lean` | The `Site`: document chrome and the route table with its proofs. |
| `Fmxai/Map/Data.lean` | **The map's data.** Edit this to add an organisation or category. |
| `Fmxai/Map/Geometry.lean` | Integer geometry: points, circles, boxes and the overlap predicates. |
| `Fmxai/Map/Circles.lean` | Fixed-point port of the force simulation that places the category circles. |
| `Fmxai/Map/Search.lean` | The verified pick-one-from-each backtracking search that replaced Z3. |
| `Fmxai/Map/Layout.lean` | `Layout.Valid`, the solver, and `solve_valid`. |
| `Fmxai/Map/Verified.lean` | The kernel computes the layout of the real data and proves it exists. |
| `Fmxai/Map/Render.lean` | Layout to inline SVG. |
| `public/` | Static files copied verbatim into `dist/`: CSS, images, favicon, `CNAME`. |
| `Main.lean` | `build` and `serve`. |
| `Test.lean` | Executable checks and the axiom audit. |

## What is verified

Everything the library proves applies to this site: every page's HTML is produced by a
printer with a proven inverse (`Sites.Site.parse_html`), the build writes exactly the listed
files (`Sites.Site.build_pages`), and internal links are values of `Fmxai.Route`, so a link to
a page that does not exist is a type error. (The old 2026 page had a link to
`https://https://fmxai.org/` and an unclosed `<a>`; neither is expressible now.)

The map adds its own story. A map is *truthful* when a dot is inside a circle exactly when
the organisation is in that category, and *legible* when nothing overlaps. Both are written
down as `Fmxai.Map.Layout.Valid`:

- circles are exactly the categories, and two circles overlap only if some organisation is in
  both;
- dots are exactly the organisations; every dot is at least 15px inside each of its circles
  and at least 25px outside every other; dots are at least 40px apart; their labels never
  touch;
- labels are exactly the categories; no label touches a circle; no two labels touch.

Three theorems carry the claim:

1. `Fmxai.Map.choose_pairwise`, `choose_mem`, `choose_map` (`Fmxai/Map/Search.lean`):
   the backtracking search returns pairwise-compatible picks, each from its own candidate
   list, one per item. This is the part Z3 used to do; it is 15 lines of code and 40 of proof.
2. `Fmxai.Map.solve_valid` (`Fmxai/Map/Layout.lean`): whatever `solve` returns satisfies
   `Layout.Valid`. Unary constraints hold because candidates are `filter`ed by them; pairwise
   constraints hold by (1); the circle check is the one run-time test in the pipeline, since
   the force simulation has no specification.
3. `Fmxai.Map.theLayout_valid` (`Fmxai/Map/Verified.lean`): the published map is valid.
   Its input, `solve_orgs_isSome`, is proven by `decide +kernel`: Lean's kernel evaluates the
   whole pipeline on the real data (about a minute) and confirms it yields a layout. The
   executable recomputes the same total function and prints its coordinates verbatim into the
   SVG, which `Test.lean` checks.

The geometry is all integers compared squared, so the specification has no floating point
and no rounding. The text-box sizes are estimates (10px and 9px per character, as in the old
JavaScript), and that is the one place the specification is a model of the browser rather
than a fact about it.

Nothing uses `partial`, `noncomputable`, `unsafe`, `implemented_by`, `native_decide`, `sorry`
or new axioms; `scripts/check.sh` greps for them, `Test.lean` pins the axioms of each theorem,
and `leanchecker` re-checks the compiled proofs independently of the elaborator.

## Editing the site

- Prose and markup: `Fmxai/Pages/*.lean`. Elements are functions named after their tags,
  strings are text, `a [.href (.route .y2026)] ["2026"]` is an internal link.
- Styling: `public/styles.css` (event pages) and `public/map.css` (the map). Kept as plain CSS
  so that the site looks exactly as it did.
- Map data: `Fmxai/Map/Data.lean`. If a change makes the map impossible to draw truthfully,
  `Fmxai/Map/Verified.lean` fails to compile instead of publishing a misleading map.

## Deployment

GitHub Pages, from the `dist/` artifact built by `.github/workflows/pages.yml` on pushes to
`main`. `public/CNAME` keeps `fmxai.org` pointed at it. The repository's Pages source must be
set to *GitHub Actions* rather than a branch.

The `sites` dependency is pinned in `lake-manifest.json` to a commit on its `master` branch.
